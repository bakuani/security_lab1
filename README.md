# Лабораторная работа № 1: защищённое REST API

API личных учебных задач: пользователь входит в систему, просматривает свои задачи и меняет их статус. Реализация: Java 21, Spring Boot 3.5.16, Maven Wrapper 3.9.11, Spring Security и Spring JDBC. Данные хранятся в реляционной H2 в памяти и сбрасываются при перезапуске. Проект выполнен Джохадзе Анной Бекаевной, группа P3410, по дисциплине «Информационная безопасность».

## Запуск

Нужны JDK 21 и доступ к Maven Central. Устанавливать Maven отдельно не требуется: Wrapper загружает закреплённую версию. Для Windows PowerShell:

```powershell
$env:JAVA_HOME = 'C:\Program Files\Java\jdk-21'
.\scripts\start-demo.ps1
```

Для Linux/macOS:

```sh
export JAVA_HOME=/path/to/jdk-21
sh scripts/start-demo.sh
```

Сервис слушает http://127.0.0.1:8080. Скрипт создаёт случайный ключ JWT и независимые случайные пароли alice и bob; пароли выводятся в локальный терминал. Пользователи и три начальные задачи создаются при запуске. У alice две задачи, у bob одна. Одна задача содержит специально добавленную XSS-строку для проверки экранирования.

Можно заранее задать переменные LAB_JWT_SECRET, LAB_ALICE_PASSWORD и LAB_BOB_PASSWORD. Для JWT требуется не менее 64 байт секрета; для паролей — от 12 символов до 72 байт UTF-8. При отсутствии переменных запуск напрямую через Maven завершится ошибкой. Ключ не выводится в журнал и не сохраняется в репозитории.

## API и примеры запросов

Все запросы и ответы используют JSON. В таблице перечислены три реализованных метода.

| Метод | Путь | Доступ | Назначение |
|---|---|---|---|
| POST | /auth/login | Без JWT | Выдать токен по логину и паролю |
| GET | /api/data | Bearer JWT | Получить задачи владельца токена |
| PATCH | /api/data/{id}/status | Bearer JWT | Изменить статус своей задачи |

Вход: подставьте пароль alice из терминала запуска.

```http
POST /auth/login
Content-Type: application/json

{"username":"alice","password":"<пароль alice>"}
```

Успех: HTTP 200, поля accessToken, tokenType со значением Bearer и expiresIn со значением 900 (секунд). Неверные реквизиты дают HTTP 401 с одинаковым сообщением для существующего и неизвестного пользователя.

```http
GET /api/data
Authorization: Bearer <accessToken>
```

Успех: HTTP 200 и массив объектов с полями id, title, description, status. Без действительного токена оба защищённых метода возвращают HTTP 401. Статус — одно из значений OPEN, IN_PROGRESS, DONE.

```http
PATCH /api/data/1/status
Authorization: Bearer <accessToken>
Content-Type: application/json

{"status":"DONE"}
```

Успех: HTTP 200 и {"status":"DONE"}. Несуществующая или чужая задача даёт HTTP 404. Неверный статус, неположительный id, пропущенные обязательные поля и неизвестные JSON-поля дают HTTP 400. Владелец определяется сервером; передать ownerId в теле нельзя.

Проверка через curl (Bash; переменные ALICE_PASSWORD и TOKEN задаются локально):

```sh
curl -i http://127.0.0.1:8080/api/data
curl -sS -X POST http://127.0.0.1:8080/auth/login \
  -H 'Content-Type: application/json' \
  -d "{\"username\":\"alice\",\"password\":\"$ALICE_PASSWORD\"}"
curl -i http://127.0.0.1:8080/api/data \
  -H "Authorization: Bearer $TOKEN"
curl -i -X PATCH http://127.0.0.1:8080/api/data/1/status \
  -H "Authorization: Bearer $TOKEN" \
  -H 'Content-Type: application/json' -d '{"status":"DONE"}'
```

В PowerShell используйте curl.exe либо готовую коллекцию postman/lab1.postman_collection.json. Коллекция сохраняет полученные токены в переменные окружения Postman; исходные пароли в экспортируемом окружении пустые.

## Реализованные меры защиты

### SQL-инъекции

Database.java использует Spring JdbcTemplate и фиксированные SQL-запросы с параметрами «?». Значения логина, идентификаторов, текста задачи и статуса передаются отдельно; JdbcTemplate создаёт PreparedStatement и связывает параметры. Конкатенации пользовательских значений с SQL нет. Например, поиск пользователя выполняется запросом SELECT ... WHERE username = ?. Строка alice' OR '1'='1' -- ищется как буквальный логин и не меняет условие запроса.

### XSS и обработка ввода

В TaskView.from все строковые поля задач экранируются HtmlUtils.htmlEscape при формировании ответа. Например, <script> превращается в &lt;script&gt;, а кавычка — в &#39;. В базе хранится исходный текст, поэтому повторное чтение не вызывает двойного экранирования. В ответах об ошибках используются фиксированные сообщения, исходный ввод не отражается.

API возвращает application/json. Spring Security добавляет X-Content-Type-Options: nosniff, Content-Security-Policy: default-src 'none'; frame-ancestors 'none' и X-Frame-Options: DENY. Интерфейсу, использующему API, следует вставлять строки через textContent; HTML-экранирование не заменяет контекстную защиту внутри JavaScript или URL. Bean Validation проверяет обязательные поля и размеры; Jackson отклоняет неизвестные поля, а статус ограничен enum.

### Аутентификация и контроль доступа

Пароли сохраняются в app_user.password_hash только как BCrypt-хэши с индивидуальной солью и стоимостью 12. Перед BCrypt проверяется лимит 72 байта UTF-8. Для неизвестного пользователя выполняется проверка фиктивного хэша, чтобы уменьшить различие времени ответа. DTO скрывают пароли и токены в toString.

После успешного входа NimbusJwtEncoder выдаёт JWT с подписью HS256 на 15 минут. JWT содержит числовой sub, iss, aud, iat, exp и случайный jti; пароля в нём нет. JWT подписан, но не зашифрован. Секрет поступает из LAB_JWT_SECRET. При перезапуске со сменой секрета прежние токены перестают проходить проверку.

Spring Security BearerTokenAuthenticationFilter и NimbusJwtDecoder проверяют подпись, допустимый алгоритм HS256, срок действия без льготного интервала, издателя security-lab1, аудиторию task-api, обязательные даты и числовой sub. Токены без подписи, с другим алгоритмом, неверными claims или сроком жизни более 900 секунд отклоняются. Оба защищённых маршрута проходят через эту цепочку фильтров.

Условие owner_id = sub применяется и при чтении, и в атомарном UPDATE статуса. Подменить владельца через JSON нельзя. Чужая и отсутствующая задача возвращают одинаковый 404. Остальные маршруты запрещены; H2 Console отключена. Приложение не создаёт HTTP-сессии, не использует cookie-аутентификацию, HTTP Basic и форму входа. CSRF отключён для API с явно передаваемым Bearer-заголовком. Ответы имеют Cache-Control: no-store.

Учебный режим ограничен localhost. Для внешнего развёртывания потребуются HTTPS, ограничение частоты входа, постоянная БД и механизм отзыва токенов. Короткий срок действия JWT ограничивает, но не устраняет риск использования украденного токена.

## Автоматическая проверка и CI/CD

Workflow .github/workflows/ci.yml запускается при push и pull request; также доступен workflow_dispatch. Используется Java 21, Actions закреплены по SHA, права GITHUB_TOKEN ограничены чтением. Два задания выполняются независимо.

### SAST: SpotBugs и Find Security Bugs

Статический анализ Java-байткода выполняет SpotBugs 4.10.5.0 с Find Security Bugs 1.14.0. Установлены effort=Max и threshold=Low. Любое предупреждение вне явно обоснованных исключений блокирует сборку. Перед SAST выполняются интеграционные тесты и сборка JAR. Отчёты XML/HTML и результаты JUnit доступны в артефакте tests-and-sast; сводка публикуется на странице задания.

В config/spotbugs-exclude.xml документированы три узких вида исключений: информационный перечень Spring-маршрутов SPRING_ENDPOINT; EI_EXPOSE_REP2 только в конструкторах трёх Spring-компонентов, которые получают общие инфраструктурные зависимости; SPRING_CSRF_PROTECTION_DISABLED только в методе configureBearerCsrf для stateless Bearer API без cookie-аутентификации. Работоспособность контроля доступа проверяется HTTP-тестами. Потенциально опасная ручная запись JSON в ответ заменена сериализатором Jackson; замечания к null-проверкам JWT устранены в коде.

```sh
./mvnw -B -ntp verify spotbugs:spotbugs spotbugs:check
```

### SCA: OWASP Dependency-Check

OWASP Dependency-Check 13.0.0 проверяет зависимости по официальным NVD 2.0 data feeds. Начальная загрузка базы может занимать несколько минут; далее используется кэш с обновлением. NVD API key не требуется. Дополнительный Sonatype OSS Index отключён, поскольку требует отдельной учётной записи; анализ NVD включён. Порог блокировки — CVSS 7.0: High/Critical и ошибки сканера завершают задание с ошибкой. Подавления CVE в SCA не используются.

```sh
./mvnw -B -ntp dependency-check:check
```

HTML/JSON сохраняются в артефакте sca-report даже при обнаружении уязвимостей. Успешный результат относится к проверенным версиям и состоянию базы на дату запуска; он не является доказательством отсутствия всех возможных уязвимостей.

## Проверка API

Интеграционные тесты ApiSecurityTest запускают настоящий HTTP-сервер на случайном порту и H2. Проверяются успешный вход, BCrypt и соль, чтение и смена статуса, SQLi, экранирование XSS, изоляция владельцев, валидация, защитные заголовки и отказ по некорректным JWT. Проверки не используют подменённую аутентификацию.

Дополнительно воспроизводимый сценарий отправляет реальные запросы curl и сверяет коды и тела ответов. Он создаёт случайные локальные реквизиты, запускает собранный JAR и останавливает его после проверки:

```powershell
.\mvnw.cmd -B -ntp verify
python scripts/smoke-test.py --start
```

Нужны Python 3 и curl. Протокол и JSON сохраняются в target/smoke без паролей и JWT. Для уже запущенного сервера передайте LAB_ALICE_PASSWORD и LAB_BOB_PASSWORD и уберите --start.

## Ответы на контрольные вопросы

1. BCrypt предпочтительнее обычного SHA-256 для паролей: индивидуальная соль мешает предварительным вычислениям, а настраиваемая высокая стоимость замедляет перебор. SHA-256 специально рассчитан на быстрое вычисление.
2. SAST анализирует исходный код или байткод без выполнения приложения; DAST проверяет поведение запущенного сервиса HTTP-запросами. Эти подходы находят разные классы ошибок и дополняют друг друга.
3. JWT состоит из заголовка, payload с claims и подписи. Сервер проверяет подпись доверенным ключом и ожидаемые claims, включая exp, iss и aud. Payload доступен для чтения без ключа; подпись обеспечивает целостность, а не конфиденциальность.
4. Без аудита зависимостей исправный собственный код может оставаться уязвимым из-за сторонних компонентов. Известные CVE в транзитивной библиотеке могут привести к утечке данных, обходу доступа или выполнению кода; поэтому SCA запускается регулярно.
